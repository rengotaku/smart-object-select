# ADR 0003: 新しいテストは実装を壊して赤くなることを確認してから採用する

## 背景

このリポジトリのテストは jsdom 上で動く。jsdom は DOM の一部しか実装しておらず、**未実装の API がエラーではなく「何もしない」挙動になる**ものがある。この性質が、通ってはいるが何も検証していない「空虚なテスト」を生む。

実際に踏んだ例:

`<input type="file">` の value をクリアする修正（同じファイルを選び直せるようにするもの）に対し、「同じファイルを2回選んで2回ハンドラが呼ばれるか」を検証しようとした。しかし **jsdom はブラウザの「値が同じなら change を発火しない」挙動を再現しない**ため、このテストは修正の有無にかかわらず通る。さらに `fireEvent.change` は jsdom 上で input の `value` を設定しないため、`value === ""` を見るテストも常に通ってしまう。

つまり「テストが緑」と「修正が効いている」の間に相関が無い状態が、気づかないまま成立していた。

同種のリスクは他にもある:

- `HTMLCanvasElement.getContext` / `toBlob` — jsdom 未実装。モックしないとテストが書けず、モックの作り方次第で何も検証しない形になりうる
- `getBoundingClientRect` — jsdom は常に全ゼロを返す。モックし忘れると、座標変換のテストが「rect がゼロなら null を返す」経路に落ちて**偽陽性で通る**
- `URL.createObjectURL` / `revokeObjectURL` / `ClipboardItem` — jsdom に存在しない

## 決定

**新しく書いたテストは、対象の実装を一時的に壊すと実際に赤くなることを確認してから採用する。** 確認結果（何を壊したら何が赤くなったか）は完了報告に残す。

TDD の「先に赤を見る」と目的は同じだが、**修正系のタスクでは実装が既に存在するため、通常の TDD だけでは赤を経由しない**。そこを補う運用として明示する。

赤にならない場合、そのテストは検証手段として機能していないので、**テストの設計をやり直す**（実装を通すために期待値を緩めるのではない）。

あわせて、テストを書くときの既定として:

- **jsdom が実装していない API に依存する箇所は、DI で差し替えられる形にする**。`pixelsToPngBlob(pixels, createCanvas?)`、`triggerDownload(blob, filename, doc?)`、`copyImageToClipboard(blob, clipboard?)` のように、DOM に触る部分を引数で受け取る
- **DOM 依存が避けられないモジュールは coverage から除外する**（`sam.worker.ts` / `transformersLoader.ts` / `imageLoader.ts`）。除外の理由は `vitest.config.ts` にコメントで書く
- **具体的なピクセル値・具体的な引数でアサートする**。「アルファが 0 でない」のような緩い条件は、RGBA の並び順の取り違えを検知できない

## 捨てた案

**カバレッジ率で品質を担保する**
このリポジトリは行カバレッジ 90% を超えているが、上記の空虚なテストはカバレッジ上「通っている行」として数えられる。**カバレッジは実行の証拠であって検証の証拠ではない**。

**mutation testing ツール（Stryker 等）を導入する**
考え方は同じ（実装を変異させてテストが落ちるか見る）だが、導入と実行時間のコストが MVP に見合わない。手動で対象を絞って行う運用から始める。将来テストが増えたら再検討の余地がある。

**jsdom をやめて実ブラウザでテストする（Playwright component testing 等）**
jsdom の未実装 API という原因そのものは消えるが、テストの実行時間が桁違いになり CI が遅くなる。**単体テストは jsdom + DI で書き、実ブラウザは統合確認（可視サーフェス）に使う**という分担にした。

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: 確認の手段。mutation testing ツールを入れて自動化するのは、この決定の趣旨に沿った強化であって置き換えではない
- **変えてよい**: coverage 除外の顔ぶれ。DOM 依存が解消されたファイルは除外から外してよい
- **壊すと危ない**: **`getBoundingClientRect` をモックせずに座標変換のテストを書くこと**。全ゼロが返り、ゼロ除算ガードの経路に落ちて偽陽性で通る
- **壊すと危ない**: 実装を通すためにアサーションを緩めること。緩めた瞬間、そのテストが守っていた保証が消える
- **壊すと危ない**: 「テストが緑だから動く」で完了報告すること。**UI に出る変更は実ブラウザの画面で、書き出しは出力ファイルの中身で確認する**
